Project name: ContextPilot (working name; verify naming and trademark availability before commercial release)
Product type: Local-first developer tool, universal AI CLI, context optimization engine, and web dashboard.
Primary objective: Build a production-quality tool that helps developers reduce unnecessary AI token consumption, preserve useful context across long coding sessions, improve prompts before submission, and measure actual or estimated savings across supported AI providers and coding agents.
Core principle: Reduce wasted tokens without reducing task quality.
Do not build a token counter that merely displays statistics. Build a functional optimization system that measures, improves, and manages AI context wherever the relevant integration technically permits.
Act as the principal software architect, senior Rust engineer, full-stack developer, AI integration engineer, UX designer, QA engineer, and security reviewer.
You are responsible for implementing a complete, functional product rather than returning a plan, mockup, prototype, or collection of disconnected examples.

2. Preserve existing user work and follow the repository's AGENTS.md, README, and project-specific instructions.

ContextPilot is a universal AI development efficiency toolkit that combines:
1. A native developer CLI.
2. A context and token optimization engine.
3. A prompt improvement engine.
4. Automatic context compaction for managed sessions.
5. Supported integrations with external AI tools.
6. A local-first web dashboard.
7. Transparent cost and savings analytics.
8. A privacy-preserving project memory and checkpoint system.
The tool should help developers answer these questions:
- How many tokens does my current task consume?
- How much context is being sent repeatedly?
- Which files and tool outputs are wasting context?
- Can my prompt be shorter without losing requirements?
- When should a session be compacted?
- What information must survive compaction?
- Which provider or model is the most cost-efficient for my workload?
- Did optimization actually save tokens or money?
- Did the optimization increase retries or degrade task quality?
- Can I resume a task after compaction or restarting the terminal?
- Can I use the same workflow across different AI providers?
Build a provider-independent tool, not a wrapper exclusively for one AI vendor.
Support different providers through adapters. Users should not be required to use one specific model, API provider, or coding assistant.
The core local features must remain useful even if the user has no AI API key.
Build both applications as parts of one product with a shared engine.

Implement a configurable context budget system.
- Track context usage against the configured model limit.
- Configure warning, compaction, and emergency thresholds.
- Reserve space for the expected response and tool outputs.
- Account for system instructions and other known context overhead.
- Distinguish estimated context usage from actual provider-reported usage.
- Warn when the selected context limit is unknown or uncertain.

Suggested initial defaults:
- 60%: show context usage and optimization opportunities.
- 75%: recommend compaction.
- 85%: compact a managed session when safe and enabled.
- 95%: stop adding optional context and warn the user.
These are configurable starting points, not universal model limits.

Implement real compaction for sessions managed by ContextPilot.
1. Inspect the session state.
2. Estimate or obtain current context usage.
3. Identify duplicated, stale, irrelevant, and resolved material.
4. Extract the active task and its constraints.
5. Preserve important decisions and verified state.
6. Compress long outputs into useful summaries.
7. Preserve unresolved questions, failed tests, and outstanding work.
8. Produce a structured continuation checkpoint.
9. Validate the checkpoint against the original requirements.
10. Replace only the managed continuation context.
11. Resume the task using the compacted context.
12. Record the operation and its token measurements.

- Original prompt token estimate.

For comparable token measurements:
Tokens reduced = baseline tokens - optimized tokens
Reduction percentage = (tokens reduced / baseline tokens) × 100
When baseline tokens are zero, undefined, or not comparable, do not display a misleading percentage.
For monetary estimates, use the relevant provider's applicable price record and billing categories.
Account for optimization overhead and any extra model calls.
Report separately:
- Gross tokens reduced.
- Optimization tokens consumed.
- Net tokens reduced where comparable.
- Estimated monetary savings.
- Provider-reported monetary savings when available.
- Actual task quality and verification evidence.
A shorter prompt does not prove lower total task consumption. An optimized request may cause additional retries or worse results.
